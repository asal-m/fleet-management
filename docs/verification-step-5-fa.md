# قدم پنجم؛ ابطال هدفمند کش و کاهش انتظار نامرتبط (M4)

تاریخ تکمیل گزارش: ۲۰۲۶-۱۰-۰۹؛ اندازه‌گیری قبل از اصلاح در ۲۰۲۶-۱۰-۰۸ انجام شد.
کد بر پایهٔ commit `3a61cf094e1efb49566e8ee3238a948f412b29da` و تغییرات محلی
قدم‌های قبلی است. تغییرات هنوز commit/push نشده‌اند.

## چه تغییر کرد و چرا

۱. MissionWorkflow نسخه را فقط هنگام تغییر HasActiveReservation افزایش می‌دهد.
Schedule و Start مجموعهٔ خودروهای آزاد را تغییر نمی‌دهند؛ قبلاً به‌خاطر هر
تغییر Mission کش باطل می‌شد. Audit تغییرهای واقعی همچنان ثبت می‌شود.

۲. VehicleWorkflow قبل/بعد IsOperationalForAssignment را مقایسه می‌کند؛ ثبت
خودرو فقط در حالت Active نسخه را افزایش می‌دهد. تعمیر Inactive یا تغییر وضعیت
پایه هنگام تعمیر، عضویت available را عوض نمی‌کند و اکنون ابطال اضافی ندارد.

۳. RegisterDriver دیگر به coordinator خودرو وابسته نیست، قفل آن را نمی‌گیرد و
نسخهٔ کش خودرو را افزایش نمی‌دهد. ثبت، aggregate تازه با ID تولیدشده در سرور
است؛ eligibility یا رزرو منابع موجود را تغییر نمی‌دهد. middleware همچنان مالک
تراکنش است. GET available drivers کش نسخه‌دار خودرو را استفاده نمی‌کند.

جدول اثر تمام commandها و دلیل حفظ قفل Assign/تعمیر/گذارهای Mission در
[D18](decisions/D18-availability-revision-and-coordination.md) آمده است. این قدم
قفل سراسری تخصیص را با قفل ریزتر جایگزین نمی‌کند. قرارداد HTTP/gRPC، roleها،
Domain، قواعد رزرو، indexهای یکتا، migrationها و بسته‌های MP Core تغییر نکردند.

## شاهد قبل از اصلاح

در اجرای `811fdfec9a644dcebe3a3950a63404ce` سه آزمون جدید، بدون skip اجرا شدند:
دو شکست مورد انتظار و یک اندازه‌گیری موفق. ثبت خودروی Inactive، برخلاف انتظار
delta صفر، نسخه را ۱ افزایش داد. هشت ثبت راننده هنگام نگه‌داشتن advisory lock
با connection جدا، ظرف ۳ ثانیه تمام نشدند؛ پس از rollback قفل، درخواست‌ها تمام
شدند و fixture منابع خودش را پاک کرد. assertionها برای پاس‌شدن ضعیف نشدند.

شمارش اولیهٔ spanهای Npgsql تمام SQL را پوشش نمی‌داد و برای جدول قبل/بعد استفاده
نشد. شمارندهٔ مستقیم DbCommandInterceptor اضافه شد. یک تلاش میانی به دلیل
nullable بودن امضای ScalarExecutedAsync کامپایل نشد؛ پس از اصلاح، build با صفر
خطا و هشدار موفق شد. baseline معتبر با شناسهٔ
`91bbb41024c24487b8962fc7728e14f8` فقط آزمون اندازه‌گیری را اجرا و پاس کرد.
گزارش‌های صفرِ دو پروژهٔ دیگر در این اجرای filtered، شاهد اجرای کامل نیستند.

## روش اندازه‌گیری

یک میزبانی واقعی source فعلی در TestServer، JWT/RSA واقعی، PostgreSQL/Redis واقعی
و volumeهای خالی استفاده شد. شماره‌ها فقط از فرمان‌های اجراشدهٔ EF جمع شدند؛
SQL، token و رشتهٔ اتصال وارد خروجی اندازه‌گیری نشدند. ترتیب workload:
یک GET سرد با limit=199، بیست GET گرم، ده ثبت راننده همراه GET و هشت ثبت راننده
هنگام نگه‌داشتن advisory lock به مدت ۳۵۰ میلی‌ثانیه. آزمون‌های این مجموعه با
نوشتن تست‌های دیگر هم‌زمان نمی‌شوند تا delta نسخه و شمارنده‌ها مخلوط نشوند.

زمان cold شامل آماده‌سازی مسیر است؛ زمان‌های TestServer، JIT، PostgreSQL محلی و
شبکهٔ Docker معادل latency عملیاتی نیستند. نمونهٔ p95 با تعداد کم، شاهد SLO یا
ظرفیت production نیست. cache hit هنوز دو خواندن نسخه از DB دارد.

نتایج عددی و شناسهٔ دو اجرا در [دادهٔ اندازه‌گیری](measurements/m4-before-after.json)
محفوظ‌اند؛ TRX کامل در `.scratch/full-suite/<run-id>/results` محلی است.

۱۶ container، نام هر ۱۷ volume و نام builderهای اولیه را برابر یافت؛ کش مشترک
هنوز ۱۴۶ رکورد / 6.909 GB است. منابع توسعه یا دیگر پروژه‌ها reset یا حذف نشدند.

بهینه‌سازی محدود M4 پیاده و محلی تأیید شد. بازطراحی قفل منابع و پذیرش ارزیاب
از این نتیجه استنتاج نمی‌شود.

کنترل تحویل: `git diff --cached --check` موفق بود؛ ۱۱۷ لینک محلی در ۴۴ فایل
Markdown بررسی شدند و هدف‌هایشان در index موجودند. دادهٔ JSON اندازه‌گیری با
خروجی مشاهده‌شده تطبیق داده شد. فایل‌های این قدم staged هستند؛ commit/push
انجام نشده و Postmanهای قبلی untracked باقی مانده‌اند.

## محدودیت و ادامه

cache factory، TTL، بازبینی نسخه، fallback Redis و شمارندهٔ تراکنشی تغییر نکردند.
قطع/وصل Redis در این قدم دوباره اجرا نشده است؛ شاهد قبلی مربوط به نسخهٔ همان
اجراست. تست کش دو میزبان و رقابت‌های تخصیص/تعمیر در مجموعهٔ کامل اجرا می‌شوند.
آزمون ثبت مستقل راننده، ادعای پیشرفت Assignهای دارای منابع مستقل نیست.

به دلیل محدودیت دانلود ثبت‌شده در قدم چهارم، imageهای محلی قدم سوم برای آماده‌کردن
وابستگی‌ها و readiness استفاده شدند. **تست‌های HTTP/gRPC از source اصلاح‌شدهٔ
فعلی روی میزبان build و اجرا می‌شوند؛ container application، نسخهٔ جدید M4 نیست.**
Docker image جدید محصول، build سرد با builder اختصاصی و native Linux CI در این
قدم تأیید نشده‌اند. سرویس توسعهٔ متوقف‌شده، نسخهٔ جدیدِ در حال اجرا معرفی نمی‌شود.
بازطراحی قفل resource/mission و deadlock/isolation testing مربوط به همان طراحی
آینده است؛ بهینه‌سازی محدود این قدم شرطاً جای آن را نمی‌گیرد.
