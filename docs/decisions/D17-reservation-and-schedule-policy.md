# D17؛ رزرو انحصاری و نقش زمان برنامه‌ریزی (M3)

تاریخ: ۲۰۲۶-۱۰-۰۸. وضعیت: سیاست موجود مستند و آزموده و مسیر حداقلی اصلاح M3 آماده شده؛
پذیرش ساده‌سازی با ارزیاب است. مدل زمانی تازه یا قاعدهٔ کسب‌وکار تازه اضافه نشده است.

## تطبیق با فایل اصلی چالش (۲۰۲۶-۱۰-۰۹)

فایل `Fleet_Operations_Backend_Engineering_Code_Challenge.md` در بند ۶ فقط
Scheduled Time را در داده‌های الزامی مأموریت آورده و طراحی دقیق چرخهٔ عمر را
به پیاده‌ساز سپرده است. بندهای ۴، ۵ و ۷ جلوگیری از مأموریت متعارض و تخصیص
منابع غیرقابل‌دسترس را الزام می‌کنند؛ زمان پایان، مدت مأموریت، بازهٔ نیمه‌باز،
ممنوعیت شروع زودتر و رفتار تأخیر واقعی را تعیین نمی‌کنند.

نتیجهٔ بررسی: رزرو انحصاری فعلی روشی محافظه‌کارانه برای جلوگیری از تعارض است؛
امکان رزرو چند مأموریت آیندهٔ غیرهم‌پوشان را ندارد. مستندسازی و تست این محدودیت
مسیر حداقلیِ مطرح‌شده در M3 ریویو است. ساخت مدل بازه‌ای، قابلیت اضافه محسوب
می‌شود و قواعد آن را نمی‌توان به فایل چالش نسبت داد. درخواست قبلی کاربر برای
داشتن هر دو مدل ثبت‌شده باقی است؛ این بررسی، پیاده‌سازی آن قابلیت را ادعا نمی‌کند.

## سیاست نسخهٔ فعلی

| موضوع | رفتار فعلی |
|---|---|
| Draft و Scheduled | هیچ خودرو یا راننده‌ای رزرو نمی‌کنند |
| Assign موفق | خودرو و راننده بلافاصله رزرو می‌شوند؛ تاریخ برنامه‌ریزی اثری در شروع رزرو ندارد |
| Assigned و InProgress | مالکیت انحصاری همان منابع را نگه می‌دارند |
| Complete یا Cancel مجاز | رزرو آزاد می‌شود؛ ID منابع برای تاریخچه روی مأموریت می‌ماند |
| ScheduledTime | دادهٔ برنامه‌ریزی است؛ هنگام Schedule باید آینده باشد و به UTC تبدیل می‌شود |
| Start | از Assigned مجاز است؛ رسیدن ساعت به ScheduledTime شرط شروع نیست |
| مدت و زمان پایان | در قرارداد و مدل موجود نیست؛ بازهٔ رزرو قابل محاسبه نیست |
| GET available | snapshot منابع واجد شرایط و آزاد در وضعیت فعلی، با limit؛ query بازه‌ای یا فیلتر ظرفیت مأموریت نیست |
| ظرفیت | هنگام Assign نسبت به نیاز مأموریت بررسی می‌شود؛ موجود بودن در available، کافی‌بودن ظرفیت برای هر مأموریت را تضمین نمی‌کند |

مثال: مأموریتی برای هفت روز بعد برنامه‌ریزی می‌شود. قبل از Assign، خودرو و
راننده هنوز available هستند. پس از Assign همان لحظه از available حذف می‌شوند؛
مأموریت امروز نمی‌تواند همان منابع را تخصیص بگیرد و 409 با کد رزرو متعارض
می‌گیرد. اپراتور می‌تواند مأموریت آینده را اکنون Start کند؛ پس از Complete، منابع
برای تخصیص دوباره آزاد می‌شوند. این رفتار عمداً در تست واقعی ثبت شده است.

## دلیل حفظ مدل ساده در این قدم

مدل فقط زمان برنامه‌ریزی را دارد؛ پایان یا مدت مأموریت تعریف نشده است. از یک
زمان شروع نمی‌توان بازهٔ اشغال منبع را استخراج کرد. ساختن زمان پایان پیش‌فرض
یا اجازهٔ استفادهٔ هم‌زمان منابع، تصمیم کسب‌وکاری جدید است. بنابراین این قدم
محدودیت نسخهٔ فعلی را روشن می‌کند و صحت همان رفتار را می‌آزماید. این مدل برای
نسخهٔ ساده با رزرو انحصاری قابل بیان است؛ ادعای زمان‌بندی چند مأموریت آینده روی
یک خودرو یا استفادهٔ بهینه از بازه‌های خالی ندارد. گزارش ارزیابی مستندسازی این
ساده‌سازی را به‌عنوان مسیر حداقلی مطرح کرده است.

## تصمیم‌های لازم برای مدل بازه‌ای آینده

مالک محصول باید زمان شروع/پایان یا مدت، منطقهٔ زمانی، زمان آماده‌سازی و برگشت،
تأخیر واقعی، شروع زودهنگام، تعمیر و تعریف overlap را مشخص کند. همچنین باید
روشن شود زمان ثبت‌شده تعهد برنامه است یا اجرای واقعی، و با تمدید مأموریت و
رزرو بعدی چه باید کرد. پاسخ این موارد در این قدم فرض نشده است.

پس از انتخاب مدل، طراحی قرارداد و migration و کنترل overlap دیتابیس برای هر
دو منبع، query بازه‌ای، cache key متناسب با فیلترها و تست رقابت لازم می‌شوند.
آزادسازی هنگام Complete/Cancel و سیاست Audit باید همراه آن بازطراحی شوند.
