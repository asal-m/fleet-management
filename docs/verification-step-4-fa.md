# قدم چهارم؛ اصلاح دو نقص راستی‌آزمایی و روشن‌کردن سیاست M3

تاریخ: ۲۰۲۶-۱۰-۰۸. کد بر پایهٔ commit
`3a61cf094e1efb49566e8ee3238a948f412b29da` و تغییرات محلی مراحل قبل است؛
این تغییرات هنوز commit یا منتشر نشده‌اند.

## A1؛ تطبیق گزارش با نتیجهٔ تک‌تک تست‌ها

ابزار VerifyTests اکنون علاوه بر Counters، تعداد UnitTest و UnitTestResult،
یکتایی شناسه‌ها، تطبیق شناسهٔ نتیجه با تعریف تست، Passed بودن تمام نتیجه‌ها و
تعلق تمام تعریف‌ها به assembly مورد انتظار را بررسی می‌کند. هر سه پروژهٔ
Domain، Application و Integration باید دقیقاً یک گزارش معتبر داشته باشند.

دلیل: عدد Passed در خلاصه، برای اثبات کامل‌بودن محتویات گزارش کافی نیست.
۱۲ آزمون مستقل از Docker روی همان کد اعتبارسنج اجرا شدند: یک گزارش کامل و
۱۱ حالت ناقص/نامعتبر؛ همه پاس شدند و هیچ‌کدام skip نشدند. سه گزارش اصلی قدم سوم
با ۱۴۴ نتیجهٔ Passed پذیرفته شدند. کپی دارای یک UnitTestResult حذف‌شده و Counters
دست‌نخورده اکنون با exit code برابر ۱ رد شد؛ در ممیزی قبلی همان کپی پذیرفته می‌شد.

## A2؛ جمع‌کردن منابع اختصاصی build و تست

هر اجرا builder از نوع docker-container با نام UUID همان اجرای تست دارد.
Compose با همان builder تصاویر سرویس‌ها را می‌سازد؛ finally ابتدا
`down --volumes --remove-orphans --rmi local` و سپس `buildx rm --force` را اجرا
می‌کند. حذف builder بدون keep-state، کش و volume اختصاصی آن را نیز جمع می‌کند.
پاک‌سازی builder مستقل از موفقیت پاک‌سازی Compose تلاش می‌شود؛ خطای هر کدام
اجرای نهایی را ناموفق می‌کند. builder پیش‌فرض تغییر نمی‌کند و prune سراسری نداریم.

دلیل: حذف container و volume پروژه به‌تنهایی تصاویر تولیدشده و کش build را
حذف نمی‌کرد. منابع پروژهٔ توسعه یا سایر پروژه‌ها نباید برای رفع این مشکل حذف شوند.
تصاویر مشترک دارای tag، مانند PostgreSQL، Redis و BuildKit حفظ می‌شوند.

این روش کش build تازه دارد؛ دریافت imageهای پایه و NuGet به شبکه و فضای کافی
نیاز دارد و اجرای سرد کندتر است. Compose حداقل 2.24.4 و Buildx حداقل 0.14 لازم‌اند.
مهلت build سرد ۳۰ دقیقه، دیگر فرمان‌ها ۱۰ دقیقه و پاک‌سازی هر بخش ۲ دقیقه است؛
مهلت CI به ۴۵ دقیقه افزایش یافت. قطع Docker می‌تواند مانع پاک‌سازی شود؛ ابزار
در آن وضعیت شکست را گزارش می‌کند. مسیر Ctrl+C هنوز به‌صورت تجربی آزمایش نشده است.

## M3؛ مسیر حداقلی مستندسازی ساده‌سازی زمان‌بندی

سیاست موجود در [D17](decisions/D17-reservation-and-schedule-policy.md) مستند شد.
Assign منابع را فوراً و انحصاری رزرو می‌کند؛ ScheduledTime دادهٔ برنامه‌ریزی است
و شرط زمانی Start نیست. مدل مدت یا زمان پایان ندارد. این قدم قاعدهٔ کسب‌وکاری،
Domain، migration یا قرارداد محصول را تغییر نمی‌دهد؛ پذیرش ساده‌سازی با ارزیاب است.

یک آزمون پذیرش REST با PostgreSQL و Redis واقعی اضافه شد: مأموریت هفت روز بعد
تا پیش از Assign رزروی ندارد؛ پس از Assign منابع از available حذف می‌شوند؛
تخصیص مأموریت امروز با همان خودرو 409 می‌گیرد؛ Start زودهنگام مجاز است و پس از
Complete منابع برای تخصیص مجدد آزاد می‌شوند. این آزمون رفتار فعلی را قابل بازبینی
می‌کند؛ برای پیاده‌سازی مدل بازه‌ای هنوز تصمیم مالک محصول لازم است.

## نتیجهٔ اجرای کامل

تلاش اولیه با شناسهٔ `d28305238cab47c5a36bfb3ba870d8b3` هنگام دانلود SDK به
مهلت قبلی ۱۰ دقیقه رسید؛ exit code برابر ۱ بود و هنوز تست‌ها آغاز نشده بودند.
پاک‌سازی خودکار موفق شد. بررسی مستقل پس از آن، باقی‌نماندن تصویر/منابع دارای
شناسهٔ اجرا، حفظ هر ۱۶ container و ۱۷ volume قبلی، و ثابت‌ماندن کش اشتراکی با
۱۴۶ رکورد و اندازهٔ 6.909 GB را تأیید کرد. snapshotها در
`.scratch/a2-before.json` و `.scratch/a2-after-timeout.json` محلی نگه داشته شدند.
ساخت همزمان ابزار هنگام اجرای نخست به قفل exe در Windows خورد؛ پس از پایان
آن اجرا، build نسخهٔ نهایی با صفر خطا و صفر هشدار موفق شد.

تلاش دوم ابزار نهایی با شناسهٔ `8e14b0182b5442d68a7bb34ff066024e` نیز در دانلود
بسیار کند image پایه باقی ماند. درخت فرایند build همان اجرا، پس از کنترل شناسهٔ
فرایند و نام پروژه، متوقف شد؛ ابزار exit code برابر ۱ داد و finally خودکار،
پروژه و builder و کش آن را پاک کرد. این کنترل مسیر شکست build است، نه آزمون Ctrl+C.
هیچ‌کدام از این دو تلاش به اجرای تست نرسیدند و build سرد موفق ادعا نمی‌شود.

برای بررسی مستقل کد فعلی، اجرای `bb0224b888af424c8a6767fdba9dd264` از imageهای
محلیِ قدم سوم، با tagهای اختصاصی همان اجرا، استفاده کرد. کد محصول از پایان قدم
سوم تغییر نکرده است؛ تست‌ها از source فعلی روی میزبان build شدند. PostgreSQL،
Redis، پیکربندی و هویت در volumeهای تازه، با پورت‌های تصادفی مستقل بالا آمدند؛
bootstrap، migration و readiness موفق بودند. دستور اصلی تست:

```text
dotnet test FleetCompany.FleetManagement.Backend.sln --configuration Release --verbosity minimal --logger trx --results-directory <run-directory>/results
```

رشته‌های اتصال فقط در حافظه به فرایند تست داده شدند. این اجرای کنترل‌شده با
اسکریپت محلی `.scratch/Verify-CachedImages.ps1` انجام شد؛ جای اجرای build سردِ
فرمان رسمی یا پذیرش native Linux CI نیست.

| پروژه | Passed | Failed | Skipped |
|---|---:|---:|---:|
| Domain | ۹۱ | ۰ | ۰ |
| Application | ۳۳ | ۰ | ۰ |
| Integration | ۳۳ | ۰ | ۰ |
| مجموع | **۱۵۷** | **۰** | **۰** |

اعتبارسنج اصلاح‌شده هر سه TRX را پذیرفت. این مجموعه شامل ۱۲ آزمون گزارش و یک
آزمون پذیرش M3 افزوده به ۱۴۴ تست قبلی است؛ تست‌های معماری نیز در مجموعه پاس شدند.
گزارش‌ها در `.scratch/full-suite/bb0224b888af424c8a6767fdba9dd264/results` محفوظ‌اند.

برای بررسی حذف کش واقعی، یک build کوچک FROM scratch روی builder اختصاصی همان
اجرا انجام شد؛ `buildx du` وجود کش غیرصفر را نشان داد. پس از موفقیت تست‌ها،
همان فرمان‌های پاک‌سازی Compose و builder، هر سه tag تصویر اختصاصی، پنج container،
سه volume سرویس‌ها، شبکه، container و volume کش builder را حذف کردند. تصویر کوچک
probe نیز با شناسهٔ دقیق manifest و کنترل عدم استفاده حذف شد؛ نسخهٔ نگه‌داری‌شدهٔ
اسکریپت probe از output برابر cacheonly استفاده می‌کند.

کنترل مستقل نهایی، برابری مجموعهٔ IDهای هر ۱۶ container، نام هر ۱۷ volume و نام
builderهای قبلی را تأیید کرد. هیچ تصویر یا منبع دارای شناسهٔ سه اجرای این قدم
باقی نماند. کش اشتراکی هنوز ۱۴۶ رکورد، 6.909 GB است؛ پاک‌سازی سراسری انجام نشد.
snapshot نهایی در `.scratch/a2-after-final.json` است. سرویس‌های توسعه مانند قبل
متوقف باقی ماندند و Healthy بودن آن‌ها اکنون ادعا نمی‌شود.

A1 و A2 پیاده شدند و اعتبارسنجی/پاک‌سازی در کنترل‌های محلی بررسی شد. محدودیت
باقی‌ماندهٔ این قدم، مشاهدهٔ موفقیت build سرد با builder اختصاصی و شبکهٔ مناسب
است. پذیرش Linux CI و macOS و کنترل تجربی Ctrl+C همچنان مشاهده نشده‌اند.

کنترل نهایی تحویل: `git diff --cached --check` پاس شد؛ در ۴۲ فایل Markdown،
هر ۹۴ لینک محلی به فایل یا پوشهٔ موجود در index می‌رسد. تغییرات این قدم staged
هستند و commit/push نشده‌اند؛ Postmanهای قبلی همچنان untracked باقی ماندند.
