# شاهد اجرایی قدم دوم؛ اجرای کامل تست‌ها

تاریخ: ۲۰۲۶-۱۰-۰۸. تغییرات این قدم محلی هستند و هنوز commit یا push نشده‌اند.

## چه تغییر کرد و چرا؟

ابزار `tools/VerifyTests` با C# و .NET ساخته شد تا اجرای کامل تست‌ها به PowerShell
وابسته نباشد. قبلاً نبودن تنظیمات PostgreSQL و Redis باعث skip تست‌های Integration
می‌شد و موفقیت دستور `dotnet test` الزاماً به معنی اجرای همهٔ تست‌ها نبود.

ابزار ابتدا یک پروژهٔ Compose تازه با نام تصادفی، volume خالی و پورت‌های خودکار
می‌سازد. bootstrap موجود رمزها را تولید می‌کند و برنامه migrationها را اعمال
می‌کند. ابزار تنظیمات اتصال را در حافظه می‌خواند و فقط به محیط فرایند تست می‌دهد؛
رمزها در خروجی یا فایل میزبان نوشته نمی‌شوند. پس از readiness هر سه پروژهٔ تست
اجرا می‌شوند و گزارش‌های TRX بررسی می‌شوند. وجود skip، failure، گزارش خالی یا
پروژهٔ غایب باعث خروج ناموفق می‌شود. پایان اجرا یا Ctrl+C منابع همان محیط تازه
را پاک می‌کند.

## روش اجرا

پیش‌نیاز: SDK نسخهٔ .NET 10 و Docker با Linux containers و Compose حداقل 2.24.4.
از ریشهٔ مخزن:

```sh
dotnet run --project tools/VerifyTests/VerifyTests.csproj --configuration Release
```

گزارش‌ها در `.scratch/full-suite/<run-id>/results` می‌مانند و وارد Git نمی‌شوند.
برای بررسی دوبارهٔ گزارش ذخیره‌شده:

```sh
dotnet run --project tools/VerifyTests/VerifyTests.csproj --configuration Release -- --validate-results <results-directory>
```

## نتیجهٔ مشاهده‌شده

| بررسی | نتیجه |
|---|---|
| build ابزار روی Windows | موفق؛ صفر warning و error |
| Windows؛ Domain | ۹۱ موفق |
| Windows؛ Application | ۳۱ موفق |
| Windows؛ Integration با PostgreSQL و Redis تازه | ۱۳ موفق |
| مجموع Windows | ۱۳۵ موفق؛ صفر failed و skipped |
| گزارش آزمایشی با یک تست skip | ابزار آن را رد کرد؛ exit code برابر ۱ |
| گزارش فاقد پروژهٔ Integration | ابزار آن را رد کرد؛ exit code برابر ۱ |
| Docker خارج از PATH | ابزار ناموفق شد؛ موفقیت کاذب اعلام نشد |

شناسهٔ اجرای موفق اولیهٔ Windows:
`3c9e8d7542bb4099a40391733554032e`.
اجرای دوباره با نسخهٔ نهایی ابزار، شناسهٔ
`af595fe0be1d491ebbb64510bcb10328`، نیز هر ۱۳۵ تست را با صفر skip پاس کرد؛
readiness، migration و پاک‌سازی منابع همان محیط موفق بودند.
کنترل‌های منفی روی کپی گزارش‌ها انجام شدند؛ گزارش اصلی تغییر نکرد.

پس از درخواست دوبارهٔ کاربر، اجرای کامل دیگری با شناسهٔ
`5cbd5b10050e445183be86f76600629a` و وابستگی‌های تازه انجام شد و exit code برابر
صفر بود: ۹۱ Domain، ۳۱ Application و ۱۳ Integration پاس شدند؛ failed و skipped
در هر سه پروژه صفر بودند. علاوه بر کنترل ابزار، فایل‌های TRX مستقیم خوانده شدند:
تعداد نتیجه‌های تک‌تک تست‌ها با total گزارش برابر بود و هر ۱۳۵ outcome برابر
`Passed` بود. پاک‌سازی کانتینرها، volumeها و network همین اجرا نیز موفق بود.

## محدودیت شاهد لینوکس و CI

اجرای آزمایشی داخل کانتینر Linux SDK روی Docker Desktop ویندوز، با شناسهٔ
`a96b7cd2478246878dbe7a5ff819f0bd`، ابزار را compile کرد و وابستگی‌ها را بالا آورد.
برنامه از میزبان Windows پاسخ `Healthy` داد، اما کانتینر ابزار به پورت loopback
منتشرشده روی میزبان دسترسی نداشت. readiness ابزار ناموفق شد؛ exit code برابر ۱
بود و منابع محیط آزمایش پاک شدند. این اجرا شاهد پاس‌شدن تست‌ها روی Linux نیست.

فایل `.github/workflows/verify.yml` همان دستور را روی Ubuntu اجرا می‌کند و TRXها
را نگه می‌دارد؛ اجرای واقعی آن پس از انتشار تغییرات هنوز مشاهده نشده است.
macOS نیز اجرا نشده است. بنابراین پیاده‌سازی چندسکویی آماده است، ولی پذیرش کامل
M1 به شاهد اجرای Linux در CI نیاز دارد.

این دستور مجموعهٔ خودکار فعلی را اجرا می‌کند. بررسی جداگانهٔ همهٔ درخواست‌های
REST، اتصال واقعی gRPC و قطع/وصل Redis در [گزارش قبلی](runtime-review-2026-10-08-fa.md)
ثبت شده و با اجرای این قدم دوباره ادعا نمی‌شود. اسکریپت‌های PowerShell برای آن
بررسی‌های تکمیلی باقی مانده‌اند. نام و پورت ثابت Compose توسعه هنوز موضوع M7 است.
